## Summary

Add a new **`research-access`** skill that reads the sibling **research repository** at `../research` and surfaces its research subjects, observations, and bibliography entries so they can act as **grounding** for new blog posts in this Jekyll site. The skill reads that repository **in place** and **read-only** — it never copies research artifacts into this repo and never writes back into `../research` — and follows the repo's established `-utils` execution model, delegating the mechanical read/collate work to a spawned **Haiku** subagent while the main agent decides what to pull and synthesises the grounding.

Alongside the skill, **extend the post-authoring task machinery** so a task can record which research it is grounded in. `templates/task-template.md` gains a **Research grounding** section that links one or more **research subjects** (e.g. `knowledge-systems`, `hypervelocity-engineering`), specific **bibliography entries** (citation keys such as `Zhang2025_TOIS`), and specific **observations** (`obs-NNNN`) from `../research`. The **`task-utils`** skill is extended to populate, update, and validate these links (including flagging a linked artifact that no longer exists in `../research`, mirroring its existing orphan-reconciliation check), and to invoke `research-access` when the author wants to browse or resolve grounding for the task's post.

## Rationale

The author maintains a separate **research repository** (`../research`) — an AI–human research workspace of Markdown documentation with its own conventions: top-level **research subjects** (each a directory with a `README.md`, an `observations/` log of typed findings/gaps/connections/hypotheses/questions/anomalies as `obs-NNNN.md`, and bibliography coverage), a repo-level **`bibliography/`** of per-entry files keyed `AuthorYYYY_Tag` (with an alphabetical `README.md` index), and strict research standards (never fabricate citations; label confidence as well-established / preliminary / hypothetical). That corpus is exactly the kind of grounded, cited material that should inform blog posts on this site — the `genai/`, `arch/`, and related sections overlap directly with the research subjects — but there is currently **no bridge** between the two repositories. An author writing a post has to open `../research` by hand, find the relevant subject, observations, and citations, and copy context across manually, with nothing recording which research a given post was built on.

A dedicated skill closes that gap while respecting the seam between the two repos. Reading `../research` **in place** (rather than syncing a snapshot into this repo) keeps a single source of truth in the research repository and avoids a staleness/duplication problem — the research corpus changes on its own cadence, and a copied snapshot here would silently drift. Keeping the skill **read-only** keeps the two repositories decoupled: grounding flows research → blog, and the skill never has to coordinate a cross-repo commit or mutate research state. Both choices were confirmed with the author (see Open Questions Q1, Q3).

Recording the grounding **on the task** — not just using it transiently — is what turns this from a convenience into a durable link. The repo already tracks each in-flight post as a `tasks/task-NNN-slug.md` file (plan-003) with quality gates and draft/published state; adding a **Research grounding** section to that file is the natural, git-tracked place to answer "what is this post grounded in?" so the answer survives across sessions and is visible in review. The author asked for links to **all three** artifact types — research subjects, bibliography entries, and observations (Q2) — because they operate at different resolutions: a subject frames the post's topic, an observation seeds or supports a specific claim, and a citation key backs it. `task-utils` already owns the task file and already does orphan-reconciliation against the filesystem, so extending it to manage and validate these cross-repo links (flagging a linked `obs-NNNN` or citation key that has vanished from `../research`) is a small, consistent addition rather than a new concern.

The skill follows the **`-utils` precedent** the repo already trusts (`git-utils`, `gh-utils`, `post-utils`, `task-utils`): the main agent decides what to retrieve and synthesises it, and a spawned **Haiku** subagent runs the mechanical, read-only file work in `../research` (Q4). Because the work here is purely *reading and collating* another repo's Markdown, Haiku is an even more comfortable fit than the `git mv`/index-edit work Haiku already does elsewhere.

This plan touches Claude Code internal assets (`.claude/skills/**`, `templates/**`, and `CLAUDE.md`), so execution must also produce `meta/MET-nnnn` changelog entries via the `claude-meta-changelog` skill.

## Open Questions

*All questions in this section must be answered by a human before the plan can move from `draft` to `accepted`. The `plan` skill will not promote status while unanswered questions remain.*

- [x] **Q1.** How should `research-access` reach `../research` — read it in place, or via a copied/synced snapshot in this repo?
  - **Answer:** **Read in place.** The skill reads `../research` directly at authoring time and copies nothing into this repo; the research repository stays the single source of truth. The skill treats `../research` as an assumed sibling checkout and, if it is missing, fails with a clear, handled error (telling the author to clone/checkout the research repo as a sibling) rather than guessing or degrading silently.
- [x] **Q2.** Which research artifact types should a task be able to link to?
  - **Answer:** **All three** — (1) **research subjects** (top-level directories such as `knowledge-systems`, `hypervelocity-engineering`), (2) **bibliography entries** (citation keys `AuthorYYYY_Tag`, e.g. `Zhang2025_TOIS`), and (3) **observations** (`<subject>/obs-NNNN`). Each is linked as a first-class list in the task's new **Research grounding** section; all three are optional (a post may be grounded in a subject only, or carry no grounding at all). **Identifier note (from the challenge):** observation numbering **restarts per subject** — both `knowledge-systems` and `hypervelocity-engineering` have their own `obs-0001`, `obs-0002`, … — so an observation reference **must** carry its owning subject (`<subject>/obs-NNNN`, e.g. `knowledge-systems/obs-0046`); a bare `obs-NNNN` is ambiguous and is not a valid reference. Citation keys, by contrast, come from the single flat repo-root `bibliography/` index and **are** globally unique, so they are referenced bare (`AuthorYYYY_Tag`). This asymmetry is deliberate.
- [x] **Q3.** Should `research-access` ever write back into `../research`, or stay strictly read-only?
  - **Answer:** **Strictly read-only.** The skill only reads `../research` to ground posts; it never modifies the research repository (no notes, no back-references, no commits there). Grounding is one-directional: research → blog. This keeps the two repos decoupled and avoids any cross-repo write coordination.
- [x] **Q4.** What execution model should the skill use — the repo's Haiku-subagent `-utils` precedent, or main-agent reads?
  - **Answer:** **Match the `-utils` precedent: a Haiku subagent.** The main agent decides what to retrieve (which subject, which observations, which citation keys) and synthesises the grounding; a spawned **Haiku** subagent (`Agent` tool, `subagent_type: "general-purpose"`, `model: "haiku"`, `run_in_background: false`) performs the read-only file reads/collation in `../research` and returns the collated material. This matches `git-utils`/`post-utils`/`task-utils` exactly.
