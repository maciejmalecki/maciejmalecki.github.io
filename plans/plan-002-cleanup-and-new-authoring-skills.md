## Summary

Five related pieces of authoring infrastructure. First, a small cleanup: consolidate templates by moving the plan template out of `plans/` and into the existing `templates/` folder (alongside `changelog-entry.md`), renamed to `templates/plan-template.md`, and updating the `plan` and `execute-plan` skills to point at the new path. Second, a new `adversarial-challenge` skill that red-teams a single blog post or page — adapted from the AI Fundamentals Playbook's `chapter-adversary` skill but retargeted at this Jekyll blog, using the post's own front-matter and stated thesis as its contract instead of a `book.yml` entry. Third, a new `english-correction` skill that edits an article in place to British English while matching the reflective, first-person essay tone of the recent `genai/_posts`. Fourth and fifth, two git-workflow skills that standardise the author's routine version-control operations by wrapping the `git` and `gh` CLIs respectively — each delegating the actual command execution to a spawned Haiku subagent — so branch naming, rebase-pulls, commit granularity, and pull-request creation follow a single convention.

## Rationale

The repository already keeps a `templates/` folder for reusable document templates, but the plan template lives separately at `plans/_template.md`. Unifying the two under `templates/` gives one obvious home for templates and removes the split-brain where a contributor has to know that plans keep their template in a different place from every other template. The rename to `plan-template.md` also makes the file self-describing next to `changelog-entry.md`.

The blog is increasingly essay-driven (the 2025 `genai` and `arch` posts are argument pieces, not tutorials), and the author wants a harder, falsification-first probe of a draft than a casual re-read gives — the same need the playbook's `chapter-adversary` serves for book chapters. Porting that skill's structure (threat model, challenge axes, falsification-first procedure, calibrated findings) and retargeting it from a `book.yml` contract to a post's front-matter + thesis gives a reusable "can I break this post before a reader does?" tool without inventing the methodology from scratch.

Finally, the author writes in British English with a consistent reflective voice, but drafts drift (Americanisms, inconsistent quotes, tone wobble). A dedicated `english-correction` skill that corrects spelling/grammar to British English **and** nudges tone toward the recent `genai` posts, editing the file in place, removes a repetitive manual pass. The tone anchor is deliberately the living corpus of recent posts rather than a frozen rulebook, so the target voice tracks the author's evolving style.

The author also performs the same git and GitHub operations by hand on every plan and post, with no enforced convention — the current branch `plan-001-relocate-jekyll-source`, for example, predates the `$type/$slug` scheme this plan introduces. Two thin wrapper skills capture the intended convention once: a `git-utils` skill for local operations (feature-branch creation as `$type/$slug`, rebase-only pulls, commit granularity that keeps related changes in one commit and unrelated changes in separate commits, push on demand) and a `gh-utils` skill for GitHub operations (pull-request creation among other common `gh` tasks). Both skills spawn a subagent on the Haiku model to run the actual CLI commands, keeping the fast, mechanical git/gh work off the main agent while the wrapper skill supplies the standardised recipe and guardrails.

All five skills/changes touch Claude Code internal assets (`.claude/skills/**`, and the template move is referenced by skills), so execution of this plan must also produce `meta/MET-nnnn` changelog entries via the `claude-meta-changelog` skill.

Document guardrails: never force-push or amend unprompted, never commit unrelated changes together, never push without an explicit request, and branch off `main` (not the current feature branch) unless told otherwise.
