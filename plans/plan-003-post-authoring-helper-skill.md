## Summary

Add **two** new, separately-scoped skills that together run the lifecycle of a blog post from a blank draft to a published, quality-gated article and give the author a persistent way to juggle several posts at once — plus the `tasks/` directory and templates they rely on.

The first skill, **`post-utils`**, owns the *post file* lifecycle. It **scaffolds** a new draft in a chosen content section (`arch`, `casual`, `cbm`, `genai`, `sh`) under that section's `_drafts/` folder with correct Jekyll front-matter, and **promotes** a draft to published state by moving it into the section's `_posts/` folder with a `YYYY-MM-DD-` filename prefix using a publication date of the author's choice, updating front-matter as needed.

The second skill, **`task-utils`**, owns *task management*. It maintains one Markdown file per task under a new `tasks/` directory (mirroring the `plans/` convention: a `task-NNN-slug.md` file generated from a `templates/task-template.md`, plus a `tasks/README.md` index), so the author can switch between in-flight posts easily. Each task tracks the post it owns (its section, slug, and whether it is currently in draft or published state) and the state of four quality gates that a post must pass on its way to publication: **language check** (via the `english-correction` skill), **adversarial challenge** (via the `adversarial-challenge` skill), **local build/preview** (a clean `jekyll build` with the post included), and **front-matter & links** (complete `title`/`description`/`categories` and resolving links).

Both skills follow the `git-utils`/`gh-utils` execution model — the **main agent decides what to do** and a **spawned Haiku subagent runs the mechanical file work**. `post-utils` delegates its plain file operations (scaffolding a draft, `git mv` on promotion) to a Haiku subagent; `task-utils` delegates its task-file bookkeeping (writing the task file from the template, editing the `tasks/README.md` index, flipping post state) to a Haiku subagent as well. The two reasoning-heavy gates run by **invoking the existing skills** — `english-correction` (language check) and `adversarial-challenge` (red-teaming) — which the main agent may optionally run inside a subagent purely for context isolation (model inherited); there is no separate model tier for them.

## Rationale

The repository already has the two hardest authoring tools — `adversarial-challenge` and `english-correction` (plan-002) — but nothing that orchestrates the *lifecycle* around them or helps the author work on more than one post at a time. Drafts live in per-section `_drafts/` folders and published posts in per-section `_posts/` folders with a dated filename, but the mechanical create-draft / move-to-published dance is done by hand, and the existing `rake post:create` task is not section- or `_drafts`-aware (it writes a bare header straight into a top-level `_posts/`). A dedicated skill removes that friction and makes the section/`_drafts`/`_posts` convention explicit and repeatable.

The author also has several posts in flight at once — the `genai/_drafts` folder alone holds three drafts — and needs a lightweight way to remember, per post, what has and has not been done: has the language pass run, has the post been adversarially challenged, does it build, is the front-matter complete. Backing each task with a Markdown file under `tasks/`, generated from a shared template and indexed in a `tasks/README.md`, reuses the exact pattern the repo already trusts for `plans/`: git-tracked, human-readable, reviewable in a PR, and switchable simply by opening a different task file. Tracking the four quality gates on the task turns the two existing authoring skills into checkable steps of a defined workflow rather than ad-hoc tools the author must remember to run.

Storing tasks as repo files (rather than the harness's ephemeral, session-scoped task tracker) is deliberate: a post's authoring state must survive across sessions and be visible to anyone reading the repo. The scaffold/promote mechanics live in the skills themselves (driving files via `Write`/`Edit`/`git mv`) rather than in the `Rakefile`, so they are self-contained and section-aware without depending on Ruby/Rake extensions.

Two design refinements shape this plan. **First, the concerns are split into two skills** — `post-utils` (the post *file* lifecycle: scaffold and promote) and `task-utils` (the *task* lifecycle: create/switch tasks, track post state and quality gates). Keeping them separate mirrors the repo's existing seam between `plan` (document lifecycle) and `execute-plan` (doing the work), keeps each skill's `description` sharply triggerable, and lets the author manage tasks without necessarily touching post files and vice versa. The two skills reference each other's boundary the way `git-utils` and `gh-utils` do. **Second, both skills delegate their mechanical file work to a spawned Haiku subagent** — exactly the execution model plan-002 established for `git-utils`/`gh-utils`, and no more elaborate than that. The main agent always works out the decisions (which section, the slug, the publication date, which gate to run, the next task ID); a Haiku subagent runs the deterministic file work for both skills — writing the draft/task file from the template, the `git mv` on promotion, editing the `tasks/README.md` index row, flipping post state to `published`. This is the same class of work `git-utils` already trusts to Haiku (`git mv`, commit trailers, upstream tracking), so a single tier suffices; an earlier draft of this plan proposed a Haiku/Sonnet/Opus split, but the plan challenge (Q7) found no evidenced difficulty gradient to justify the extra tiers and it was dropped. The two reasoning-heavy quality gates are handled differently: they are not "a model tier" at all but **invocations of the existing `english-correction` and `adversarial-challenge` skills**, whose method already lives in the skill itself. Running that method in a stronger-model subagent would only re-run the same instructions after a cold-start hop, so the plan does not mandate one; the main agent invokes the skill directly, optionally wrapping it in a subagent solely to keep a long correction/red-team transcript out of the main session (model inherited, chosen for isolation rather than capability). This keeps mechanical work cheap and the reasoning work exactly where the repo already puts it — in the two authoring skills.

- [x] **Q7.** Is three-tier delegation (Haiku/Sonnet/Opus) actually warranted, or is it over-engineering relative to the `-utils` precedent? `git-utils` trusts **Haiku** with `git mv`, commit-message trailers, and upstream tracking — work at least as state-sensitive as writing a templated task file and one index row, which Q5 assigns to **Sonnet**. And the check/challenge *method* already lives inside the `english-correction`/`adversarial-challenge` skills, so routing them through an **Opus** subagent adds a hop without a stated capability gain. Decide whether to keep the three tiers as specified, or simplify (e.g. Haiku for all file/bookkeeping work; main agent runs checks/challenges directly). This choice may be moot if Q6 rules out subagent-invoked skills.
  - **Answer:** **Simplify to a single Haiku tier.** All mechanical file/bookkeeping work in **both** skills goes to a **Haiku** subagent (matching the `-utils` precedent, which already trusts Haiku with more state-sensitive `git mv`/trailer/upstream work than a templated file write). The **Sonnet** bookkeeping tier is dropped — no evidenced difficulty gradient justified it. The **Opus** check/challenge tier is dropped as a *mandated* tier: quality gates are run by **invoking the `english-correction`/`adversarial-challenge` skills** (whose method already lives in the skill), and the main agent may optionally wrap a skill invocation in a subagent **only for context isolation** — model inherited/default, not Opus, and not required. Q6 confirmed the Opus path is *possible*, but it re-runs the same skill instructions after a cold-start hop, so it is not adopted. Net: one Haiku tier for files; skills-as-gates for reasoning.
- [x] **Q8.** What is the exact front-matter contract for a scaffolded draft, given the real corpus? The challenge found the plan's own exemplar (`genai/_drafts/design-by-agent.md`) has **no `description`**, only ~12 posts carry `description` at all, real posts use a `pic:` field the plan omits, and titles containing apostrophes/colons must be **quoted** (e.g. `"Why don't I feel emotional…"`). As written, the `frontmatter-and-links` gate ("`title`/`description`/`categories` complete") would fail the author's own exemplar. Decide: (a) which fields the scaffolder writes (include `pic`? quote risky titles?), and (b) whether `description` is a **required** gate condition or merely recommended.
  - **Answer:** **Scaffold a complete front-matter block with placeholders.** The scaffolder always writes the full field set observed in real posts — `title`, `layout: post`, `categories`, `description`, `pic` — filling **derivable** fields with real values (`title` from the given title, `layout: post`, `categories` defaulting to the section) and **authorial** fields with clearly-marked placeholders the author replaces before publishing (`description:` a `TODO`/placeholder sentence; `pic:` a placeholder path such as `/<section>/img/TODO.jpg`). Titles containing apostrophes, colons, or other YAML-significant characters are **double-quoted** (e.g. `title: "Why don't I feel emotional…"`); safe titles may be unquoted. **The `frontmatter-and-links` gate then means "no placeholders remain"** — `title`/`categories` present and real, and `description`/`pic` filled with genuine values (not the scaffold placeholder). So `description` and `pic` are *required to be resolved before the gate passes*, but the scaffold seeds them so nothing is silently missing. (The existing `genai/_drafts/design-by-agent.md` predates this contract and is not retrofitted; the gate applies to posts created via `post-utils`.)
- [x] **Q9.** When and how does the `build-clean` gate run, given Jekyll excludes `_drafts/` by default? A gate that must pass "with the post included" while the file is still under `_drafts/` is contradictory unless the build uses `--drafts` (which is not what CI/production runs, so it proves less). Decide: run `build-clean` **at promotion** against the real `_posts/` file (recommended), or run it earlier with `--drafts` and accept the weaker signal.
  - **Answer:** **Run `build-clean` at promotion against the real `_posts/` file, using the production command** `JEKYLL_ENV=production bundle exec jekyll build` — the same command CI runs, so a clean build means what it means in production. The gate is therefore evaluated **after** `post-utils` promotes the draft into `<section>/_posts/<date>-<slug>.md` (not on the `_drafts/` file, which Jekyll excludes by default). The weaker `--drafts` pre-check on the draft is not adopted; if the author wants an early smoke-build they can run it ad hoc, but the tracked gate is the production build on the promoted post. Consequence for promotion ordering: because this gate can only be satisfied post-promotion, it is the one gate that goes green *after* the `git mv`, whereas the other three (language-check, adversarial-challenge, frontmatter-and-links) should be green *before* it — document this ordering in `task-utils`.
